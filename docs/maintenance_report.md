# Predictive Maintenance Report
## Using AI-Based Machine Failure Predictions for Maintenance Decisions

**Project:** AI-Based Predictive Maintenance System  
**Model:** Random Forest Classifier (scikit-learn 1.4)  
**Dataset:** AI4I 2020 Predictive Maintenance Dataset (10,000 samples)  
**Report version:** 1.0

---

## 1. Overview

This report explains how the predictive maintenance system works, how its outputs should be interpreted by maintenance teams, and where the system's limitations apply.

The system analyses six real-time machine telemetry readings and outputs:
- A **binary failure prediction** (0 = no failure, 1 = failure likely)
- A **failure probability score** (0.0–1.0)
- A **confidence score** for the prediction
- A **maintenance recommendation** based on rule-based heuristics

---

## 2. How to Interpret Predictions

### 2.1 Machine Failure Flag

| Value | Meaning | Recommended Action |
|---|---|---|
| `0` | Model predicts no failure in the near term | Continue normal operations; monitor if borderline |
| `1` | Model predicts failure is likely | Initiate inspection; do not wait for scheduled maintenance |

> [!IMPORTANT]
> A prediction of `0` (no failure) does not guarantee the machine is safe. It means the model found no failure pattern in the current telemetry snapshot. Physical inspection remains mandatory at scheduled intervals.

### 2.2 Failure Probability Score

The failure probability is the model's estimated probability that the machine will fail. It is produced by the Random Forest's vote aggregation across 100 decision trees.

| Range | Interpretation |
|---|---|
| 0.00 – 0.20 | Low risk — machine appears healthy |
| 0.21 – 0.49 | Moderate risk — monitor closely, schedule soon |
| 0.50 – 0.74 | High risk — plan maintenance within 24–48 hours |
| 0.75 – 1.00 | Critical risk — stop or reduce load; inspect immediately |

### 2.3 Confidence Score

The confidence score is the probability assigned to the **winning class** (whichever class was predicted). A high confidence score of 0.95 on a prediction of `0` means the model is very certain the machine is healthy. A confidence of 0.55 on a prediction of `1` means the model is barely majority-voting for failure.

> [!TIP]
> For high-stakes decisions, require both `machine_failure = 1` AND `failure_probability > 0.65` before halting operations.

### 2.4 Maintenance Recommendation

The recommendation text is generated by a rule-based heuristic layer applied after the model prediction. It considers individual sensor readings against engineering thresholds:

| Rule | Threshold | Reason |
|---|---|---|
| Tool wear alert | > 200 min | Tool life limit for the AI4I dataset profiles |
| High torque warning | > 60 Nm | Overload stress on spindle and bearings |
| Poor cooling warning | ΔT < 8.6 K and RPM < 1400 | Insufficient heat dissipation at low speeds |
| Overspeed warning | > 2800 RPM | Mechanical stress on rotating components |

These thresholds are derived from the statistical patterns in the AI4I 2020 dataset. They are **starting points** and should be validated against actual equipment specifications.

## 3. Failure Mode Context

The AI4I 2020 dataset includes five labelled failure modes that the model was trained to predict as a combined binary outcome:

| Code | Failure Mode | Typical Cause |
|---|---|---|
| TWF | Tool Wear Failure | Tool exceeds useful life; cutting force degradation |
| HDF | Heat Dissipation Failure | Low speed with insufficient process-to-air temperature difference |
| PWF | Power Failure | Torque × speed product outside rated power envelope |
| OSF | Overstrain Failure | Tool wear × torque exceeds material strain limit |
| RNF | Random Failure | Random, not predicted by process parameters (3% of all failures) |

> [!NOTE]
> The model predicts `Machine failure` (any failure), not the individual failure type. Random Failures (RNF) are structurally unpredictable and are expected to remain as false negatives.

## 4. Operational Decision Framework

### 4.1 Recommended Response Protocol

```
Prediction received
       │
       ├─ machine_failure = 0, failure_prob < 0.30
       │    → Normal operation; log result; next check at scheduled interval
       │
       ├─ machine_failure = 0, failure_prob 0.30–0.49
       │    → Elevated monitoring; reduce check interval by 50%
       │
       ├─ machine_failure = 1, failure_prob 0.50–0.74
       │    → Schedule unplanned maintenance within 24 hours
       │    → Review recommendation text for specific component
       │
       └─ machine_failure = 1, failure_prob ≥ 0.75
            → Stop or reduce load immediately
            → Physical inspection before resuming
```

### 4.2 Integrating with Maintenance Workflows

1. **Continuous monitoring**: Call `/api/v1/predict` on each telemetry cycle (every 30–60 seconds for CNC machines).
2. **Alerting**: Trigger maintenance ticket automatically when `failure_probability > 0.70`.
3. **Audit trail**: Every prediction is logged to MLflow with the input values and timestamp, providing a complete decision audit record.
4. **Trend analysis**: Use the MLflow `Predictive_Maintenance_Inference` experiment to plot `failure_probability` over time for drift detection.

## 5. Model Performance Summary

Evaluated on 2,000 held-out test samples (20% stratified split):

| Metric | Score |
|---|---|
| Accuracy | 98.00% |
| Precision (failure class) | 91.18% |
| Recall (failure class) | 45.59% |
| F1-Score (failure class) | 60.78% |
| ROC AUC | 95.61% |

### 5.1 Interpreting Recall vs Precision

The model has **high precision (91%)** and **lower recall (46%)**. This means:

- When the model says "failure" it is correct 91% of the time (**few false alarms**)
- The model misses approximately 54% of actual failures (**many missed detections**)

This trade-off is a deliberate result of `class_weight="balanced"` combined with the natural class imbalance in the dataset (~3.3% failure rate). In safety-critical applications, adjusting the decision threshold downward (e.g., flag as failure if `failure_probability > 0.35`) would increase recall at the cost of more false alarms.

### 5.2 Confusion Matrix Interpretation (test set)

|  | Predicted: No Failure | Predicted: Failure |
|---|---|---|
| **Actual: No Failure** | 1,927 (TN) | 5 (FP) |
| **Actual: Failure** | 37 (FN) | 31 (TP) |

37 actual failures were not caught by the model. For a dataset with random failures (RNF) constituting ~30% of failure cases, this is expected.

## 6. Known Limitations

> [!WARNING]
> This system must not be used as the sole basis for safety-critical maintenance decisions without domain expert validation.

### 6.1 Dataset Limitations

- The AI4I 2020 dataset is **synthetic** (generated by simulation, not real factory data). Actual sensor distributions may differ significantly in production environments.
- The dataset covers a single machine type profile. Accuracy on different machine types, materials, or operating conditions is unknown.
- The dataset has a **3.3% failure rate**. In real environments the failure rate and its distribution may differ, changing model behaviour.

### 6.2 Model Limitations

- The model predicts **current snapshot failure probability** from instantaneous telemetry. It does not model failure trajectories over time (no time series awareness).
- **Random Failure (RNF)** events cannot be predicted by definition — they occur independently of process parameters.
- The model was trained on a static dataset. **Concept drift** (changing failure patterns over time) will degrade accuracy without retraining.
- Temperature ranges are capped at 280–320 K by the API validation. Inputs outside this range (extreme environments) will be rejected.

### 6.3 Operational Limitations

- The API produces a prediction for each request independently. If the machine's telemetry varies rapidly, a single snapshot may not represent the trend.
- MLflow logging is **best-effort**: if the MLflow server is offline, predictions still work but the audit log will have gaps.
- No authentication is implemented on the API. Deployment behind a gateway or VPN is required for production use.

## 7. Maintenance Decision Checklist

Before acting on a failure prediction, verify:

- [ ] Is the prediction confidence score above 0.70?
- [ ] Has the same machine shown elevated failure probability in the last 3 prediction cycles?
- [ ] Does the recommendation text identify a specific component to inspect?
- [ ] Has the tool wear reading been verified against the physical tool clock?
- [ ] Is a qualified maintenance technician available?

---

## 8. Contact and Escalation

This system is a **decision support tool**, not an autonomous maintenance controller. All predictions should be reviewed by a qualified maintenance engineer before equipment is halted or parts are replaced.

For model performance queries, retraining requests, or threshold adjustments, refer to the project README and the MLflow experiment tracking UI at `http://localhost:5000`.
